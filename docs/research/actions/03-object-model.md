# 对象先于动词：动作对象模型

> 目的：定义玩家能点到的“人、部门联系人、设施、物件、材料、当前事件”，以及它们如何生成候选动作。
>
> 硬判据：**动作参数必须参与结算，不能只参与文案。**每类对象都必须在资格、结果、材料、记忆或后续事件中至少承担一种真实作用；只用于显示名称的对象不算动作对象。

## 1. 总体结构

本作不先展示动作目录，而是先解析当前上下文中的对象：

```text
当前驻地 + 当前地点 + 当前时间 + 玩家身份
  → 可见对象集合
  → 玩家选中一个对象
  → 根据对象类型、状态、输入和日程生成候选动作
  → 动作七元组完整后才允许执行
```

对象不是 UI 包装，而是结算输入。一个对象至少要回答：

1. 它是谁/是什么，稳定 ID 是什么？
2. 它当前在哪里，是否仍然存在？
3. 玩家为什么能看见、接触或操作它？
4. 它能接受哪些输入，能产生哪些结果？
5. 它会记住什么，之后如何变化？

## 2. 六类对象

### 2.1 人 `Person`

`Person` 是具有持久身份的真实个体，可来自关键 Resident、派系代表或内容明确登记的联系人。

| 字段 | 含义 | 如何参与结算 |
| --- | --- | --- |
| `person_id` | 稳定身份，不用显示名作键 | 记忆、关系、任务、材料来源和生死校验都指向它 |
| `silo_id` | 所属地堡 | 防止跨堡误用同名人物和材料 |
| `name` | 玩家可见名称，未知时可隐藏 | 只负责展示，不决定权限 |
| `role_ids` | 职务、代表身份、联系人身份 | 决定其能否批准、作证、交付或请求帮助 |
| `location_ref` | 当前权威地点或 zone | 决定能否当面交谈、是否错过日程 |
| `schedule_ref` | 可见或部分可见的作息 | 决定接触窗口和替代接触方式 |
| `knowledge_scope` | 他知道什么、不知道什么 | 限制其能确认、否认或提供的 Version |
| `memory_ref` | 与玩家的互动记忆集合 | 改变话题、信任、拒绝和后续委托 |
| `life_state` | 在岗、失联、被拘、死亡等 | 失效后不能继续提供新对话或任务 |

**禁止**：用“Supply 代表”临时生成一个无 ID 的对话框。若当前没有真实人物，只能使用部门对象，不能伪造个人记忆。

### 2.2 部门联系人 `DepartmentContact`

`DepartmentContact` 是“某个真实人物在某部门中的联系角色”，不是第二种人，也不是部门本体。

```text
DepartmentContact = person_id + profession_id + contact_role + access_scope
```

| 字段 | 作用 |
| --- | --- |
| `contact_role` | 仓管、值班工程师、案件负责人、病区联络人等，限定其工作权限 |
| `access_scope` | 能看哪些库存、病例、维修、日志或申请 |
| `department_scope` | 他能为部门承诺什么，哪些只能个人表态 |
| `availability` | 当前是否可接触，是否只能通过转交材料联系 |

部门本体可以接受配给、命令、设施维护等组织性动作；对话、承诺、隐瞒和请求则必须落到联系人。若联系人不具备审批权限，玩家不能通过一次谈话获得正式批准。

### 2.3 设施 `Facility`

设施是可履职、维护、进入或使用的空间实体，例如诊疗点、配给仓、泵房、终端、会议室。

| 字段 | 含义 | 如何参与结算 |
| --- | --- | --- |
| `facility_id` | 稳定设施 ID | 动作目标、事件位置和材料来源 |
| `function` | Medical/Supply/Mechanical 等职能 | 决定基础职务和可用工具 |
| `floor_id/zone` | 权威位置，缺楼层时只保留 zone | 决定距离、日程、传播范围和事件覆盖 |
| `operating_state` | 正常、停机、封锁、损毁等 | 决定可执行动作与主结果 |
| `access_policy` | 身份、工具、门卡、许可或陪同要求 | 决定进入、使用、违规操作和痕迹 |
| `current_issue` | 当前故障、积压、公共卫生事件等 | 决定本次履职的具体问题，而非永久通用作业 |
| `linked_departments` | 使用或管理该设施的部门 | 决定谁受影响、谁能提供权限 |

**设施动作必须有当前问题。**“修泵”应绑定具体泵的故障或维护周期，而不是每月按一次同样 Overhaul。

### 2.4 物件 `Item`

物件是有物理位置、持有者和状态的东西，例如封存箱、工具、药品、门卡、打印件、维修零件。

| 字段 | 如何参与结算 |
| --- | --- |
| `item_id/item_type` | 决定能否使用、交付、拆解或查验 |
| `location_ref/holder_ref` | 决定玩家能否接触、谁发现遗失、交付后位置如何变化 |
| `legal_status` | 决定合法使用、违规持有、没收和报告路径 |
| `condition` | 完好、损坏、耗尽、伪造等，改变可用性 |
| `linked_fact_ids` | 说明它能支持哪些事实，不能自动证明哪些动机 |
| `provenance` | 来源、经手人、时间和批次，决定能否与其他材料互证 |

物件与材料不同：物件可以被拿走、耗尽或归还；Observation 是对某事的观察记录，不能因交付原件而随意消灭事实。

### 2.5 材料 `Material`

本文的 `Material` 是可用于对话、核验、公开或委托的信息载体，运行模型对接 Observation，而不是另一个碎片背包。

| 字段 | 如何参与结算 |
| --- | --- |
| `observation_id` | 一次具体观察的唯一 ID，用于去重和回溯 |
| `fact_id/version_id` | 决定它支持什么事实和解释 |
| `source_ref` | 谁、在哪个地点、经什么行为获得 |
| `channel` | 巡诊、维修、库存、对话、日志、正式档案等 |
| `reliability_scope` | 对哪些命题可靠，对哪些命题没有证明力 |
| `independence_key` | 防止同一来源转述被当作多份独立证据 |
| `disclosure_state` | 谁看过、交给过谁、是否公开、是否被撤回 |
| `legal_refs` | 能支持哪些程序或条款，不把传闻直接变成法律证据 |

材料可以选择“出示、转述、交付副本、隐瞒、组合核验”，但不同选择必须产生不同披露记录和受众结果。

### 2.6 当前事件 `CurrentEvent`

当前事件是正在发展、允许干预的世界状态，例如病区异常、配给争议、设备停机、联系人委托、审查预约。

| 字段 | 如何参与结算 |
| --- | --- |
| `event_id/definition_id` | 唯一实例与内容定义，支持完成状态和防重入 |
| `stage` | 当前阶段，决定可干预动作 |
| `participants` | 当前真实人物、部门和派系，不接受幽灵参与者 |
| `location_ref` | 事件实际发生位置 |
| `window` | 开始、到期、下一次推进时间 |
| `requirements` | 已满足和未满足的介入条件 |
| `consequence_hooks` | 每个选择实际修改哪些状态、事件与门控 |

事件不是任务标题卡。它必须随玩家行动、NPC 日程或时间推进改变状态。

## 3. 对象如何被选中

### 3.1 空间入口

玩家在剖面中选择楼层或 zone 后，先看到该处的人、设施、物件和事件，再点对象。地点只负责收窄候选集合，不自动替玩家选择动作。

```text
选中 F76–80 病区
├─ 当前事件：集中就诊
├─ 设施：诊疗点
├─ 联系人：病区联络人
└─ 物件：药品申领箱
```

### 3.2 材料入口

玩家从档案选择一份 Observation，可看到“可出示给谁知道、可在哪里核验、与哪些事件有关”。档案不会直接提供全局 Share Info，而是生成具体对象动作。

### 3.3 事件入口

事件卡只显示当前可介入的对象和时机。点击“处理”后定位到对应人、设施或材料，不直接结算整个事件。

### 3.4 搜索与返回

搜索优先搜索对象名称、地点、职能和已知材料，而不是搜索抽象动词。执行或取消后返回原对象，保留滚动位置与选择。

## 4. 候选动作生成

```text
objects = visibleObjects(context)
for object in objects:
  capabilities = capabilityRegistry.match(object.type, object.state)
  for capability in capabilities:
    candidate = bind(capability, actor, object, location, time, inputs)
    evaluate eligibility and disabled reasons
```

注册表存的是“对象类型能提供什么能力”，不是全局按钮列表。例如：

| 对象状态 | 能力模板 |
| --- | --- |
| 病区 + 集中就诊 + Medical 身份 | 巡诊、核对药品、询问患者 |
| 申领单 + 已知物流异常 | 出示、与维修单组合、归还原件 |
| 联系人 + 曾帮助 + 当前委托 | 请求转交、接受委托、拒绝委托 |
| 停机设施 + 维修权限 + 工具 | 检修、替换零件、请求停机窗口 |

## 5. 对象失效与未知状态

- 人物死亡、失联、被拘或不再值班时，相关动作立即失效，不能继续产出新材料。
- 设施损毁后，维护动作转为清理、评估或替代设施路径，不继续显示正常巡检。
- 物件被交付后，持有位置改变；没有副本就不能再次出示原件。
- 未知人物只显示玩家已确认的信息，不提前暴露日程、派系和记忆。
- 地点只知道 zone 时，不生成精确楼层材料或跨楼层路径。

## 6. 反例与验收

### 反例 A：对象只是图标

若点 Supply 仓管与 Mechanical 班长，最终都读取同一个全局 `target_dept`、调用同一关系增加、材料池也相同，则对象只参与了文案，判失败。

### 反例 B：设施只是地图背景

若诊疗点和泵房都提供“履职”按钮，最终都只增加威望，则设施没有参与结算，判失败。

### 验收

1. 更换对象 ID 会改变至少一项真实输入、结果、材料、记忆或后续事件。
2. 对象失效后，依赖它的动作不可继续执行。
3. 未知对象不会泄露未确认状态。
4. 一个对象的候选动作全部能从其类型、状态、地点、输入和日程解释。
5. 不使用“任意人”“任意设施”“任意材料”作为正式执行参数。
