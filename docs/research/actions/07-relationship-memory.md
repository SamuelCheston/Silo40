# 关系记忆：数值关系与具体互动历史并存

> 目的：让后台 Connection/Prestige 等数值继续服务门控，同时让界面能解释“你替他做过什么、瞒过什么、交出去过什么”。
>
> 硬判据：**动作参数必须参与结算，不能只参与文案。**关系记忆必须改变后续对话、准入、委托、材料回应或风险，不能只是更长的 flavor text。

## 1. 为什么数值和记忆都需要

数值适合：

- 门控阈值，例如某部门关系达到要求；
- 派生威望、接受倾向和 AI 判断；
- 快速比较多名联系人的总体状态。

记忆适合：

- 解释为什么愿意帮忙、为什么拒绝、为什么追问来源；
- 防止同一行为被无限重复刷数值；
- 让材料披露、隐瞒和举报产生不可逆的具体后果；
- 给玩家提供可回溯的关系历史。

只用数值会让关系变成刷点；只用长文本记忆会让门控和模拟难以计算。两者应通过同一个动作结果同步写入。

## 2. 三层关系模型

```text
RelationshipState：当前数值与权限
RelationshipMemory：发生过哪些具体互动
RelationshipOffer：因此当前出现哪些新话题、委托和动作
```

### RelationshipState

| 字段 | 用途 |
| --- | --- |
| `actor_id + subject_ref` | 明确是哪名玩家与哪个人/部门的关系 |
| `connection_value` | 门控和派生计算，不直接显示为唯一解释 |
| `trust_scope` | 对方愿意在哪些事上相信玩家，而非全领域信任 |
| `access_grants` | 具体准入、材料、委托和私下话题权限 |
| `current_stance` | 当前合作、警惕、拒绝等短期状态 |

### RelationshipMemory

每条记忆至少包含：

| 字段 | 含义 |
| --- | --- |
| `memory_id` | 唯一事件 ID，防重复结算 |
| `subject_ref` | 谁记住这件事 |
| `action_instance_id` | 哪个具体动作产生 |
| `kind` | help / delivery / disclosure / concealment / betrayal / refusal / trade 等 |
| `object_refs` | 涉及哪个人、物件、Observation、事件 |
| `location/time` | 何时何地发生 |
| `visibility` | 谁知道：本人、在场者、部门、公众或仅玩家 |
| `consequence_refs` | 已产生哪些权限、事件和后续结果 |

### RelationshipOffer

由状态与记忆派生当前新选项。例如：

- 曾归还维修单 → 可以询问该设备的历史改动；
- 曾替仓管核对批次 → 可以委托核对下一批；
- 曾向调查员出示材料 → 调查员会追问来源，而不是继续普通闲谈；
- 曾泄露患者说法 → 患者可能拒绝提供新证词。

## 3. 数值与记忆的写入顺序

```text
动作主结果
→ 写 RelationshipMemory（具体事件）
→ 根据记忆类型、对象、输入和历史计算 RelationshipState 变化
→ 派生新的 access_grants / offers
→ 返回 UI：数值变化摘要 + 可理解的行为记录
```

数值变化不能只由 `action_type` 决定。相同的“出示材料”动作，正式核验、归还原件和泄露隐私应产生不同记忆和数值方向。

## 4. 界面如何并存

### 4.1 联系人摘要

```text
Supply 仓管
当前：愿意在工作时间核对库存
最近：你帮他核对过异常批次；你尚未解释材料来源
[查看互动记录] [当前可做的事]
```

不必把 connection 百分比放在第一行。精确数值可保留在“查看计量”中。

### 4.2 互动记录

按时间显示真实事件：

```text
Y124 M2 · 仓库
你归还了异常申领单，并协助核对批次。
结果：开放“核对下一批库存”。

Y124 M3 · Judicial 办公室
你向调查员出示了同一单据的副本。
结果：仓管随后从调查员处得知这次披露；他对来源更加谨慎。
```

“随后”等实际时间与传播路径应由权威结算确定，不能提前编造。

### 4.3 部门关系与个人关系分开

帮助仓管不代表整个 Supply 部门都信任玩家。界面必须区分：

- 个人记忆：联系人知道什么；
- 部门认知：哪些事情已经传开；
- 公开认知：哪些事情有公开记录。

只有经过实际传播，个人互动才升级为部门或公众记忆。

## 5. 记忆如何参与后续结算

| 记忆 | 后续影响 |
| --- | --- |
| 帮助核对库存 | 开启库存核对委托；提高该联系人在物流话题上的合作意愿 |
| 归还物件 | 物件位置改变；联系人允许讨论其来源；不自动提高所有部门关系 |
| 出示材料 | 接收人可引用该材料；可能要求来源、开启核验或限制进一步传播 |
| 隐瞒材料 | 当前不披露；若对方随后从其他渠道得知，会产生额外信任后果 |
| 泄露私事 | 相关人减少私下话题，可能告知其所属群体 |
| 拒绝委托 | 记录拒绝原因和事件；不默认等于敌对，后续可因条件变化重新接触 |
| 违规进入 | 在场者或安保记录行为，影响准入与怀疑，而非普通关系扣分 |

若记忆从不被读取，它只是日志，不是关系系统。

## 6. 防刷与重复互动

### 6.1 同一互动只结算一次

`action_instance_id + subject + memory kind` 用于防重入。重复打开结果卡、读档或重新点击都不能再写一条。

### 6.2 重复话题返回已有结果

向同一人重复出示同一 Observation：

- 显示“他已经看过这份材料”；
- 保留当前可追问的新问题，但不重复接受、关系或思潮收益；
- 若材料出现新的核验状态，可以形成一条真正的新记忆。

### 6.3 不同对象不自动复制记忆

同一帮助行为施加给不同联系人时，要分别读取其诉求、权限和当前事件。不能用一个全局 `last_help_kind` 让所有人同时知道。

## 7. 记忆、谣言和暴露的关系

- 私人记忆不自动等于公开事实。
- 经手链可以让记忆传播，但每次传播都要有实际主体、时间和渠道。
- `Suspicion` 是特工全局状态，不能复制成每个联系人的同一数值。
- 联系人是否起疑应由其记忆、证据和权限决定。
- `Exposure` 属于对应 operation track，联系人记忆可以成为追查路径，但不能直接合并为一个数。

## 8. 最小实现与扩展边界

### 最小实现

1. 为每名真实联系人保存少量结构化记忆，不需要全量对话树。
2. 数值仍由后端计算，UI 显示最近关键记忆和当前新权限。
3. 每种记忆至少有一个真实消费方：新动作、拒绝原因、材料回应或后续事件。
4. 记忆随存档保存，读档后不能重复结算。

### 后置扩展

- 多步传播与部门认知；
- 长期信任领域变化；
- NPC 之间互相转述玩家行为；
- 复杂派系集体记忆。

不要首版就给所有居民生成完整人生履历。

## 9. 反例与验收

### 反例 A：记忆只是文本

界面写着“你曾帮助过他”，但后续选项仍只检查 connection 数值，记忆不影响任何结果，判失败。

### 反例 B：共享全局记忆

帮助 Supply 后，Mechanical、Medical 同时出现“你曾帮我”的对话，判失败。

### 反例 C：隐瞒等于无事发生

玩家选择隐瞒材料，系统只是不执行 Share Info，却没有记录对方是否后来得知，判失败；隐瞒至少要有当前披露状态和后续发现接口。

### 验收

1. 数值与记忆由同一动作原子写入，读档不重复。
2. 每条记忆至少改变一个后续动作、回应、权限或事件。
3. 个人、部门和公众认知不自动同步。
4. 重复出示与重复帮助不会重复产生完整收益。
5. 玩家能在 UI 看懂“现在能做什么”与“过去做过什么”的因果关系。
