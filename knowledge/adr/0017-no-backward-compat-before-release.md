# ADR-0017 · 正式上线前不承担向后兼容义务

| 状态 | 日期 | 依据 |
| --- | --- | --- |
| 已接受 | 2026-11-15 | 项目所有者裁决（会话指令下达），本 ADR 为首次落地 |

## 背景与问题

项目尚未正式上线，机制、内容与接口仍在高频迭代。存档格式、事件 ID、内容 DSL、配置键、API 形状、parity 基线每次变动若都要写迁移与兼容代码，成本全部落在开发侧而玩家收益为零，还会拖慢迭代。需要裁决明确上线前的兼容义务边界。

## 决策

- 首次公开发布之前不承担向后兼容义务，**包括存档兼容**。存档格式、事件 ID、内容 DSL、配置键、API 形状、parity/轨迹基线、前端本地状态都可以直接破坏，不要求写迁移代码。
- 存档走**硬切断**：破坏性变化直接提升 `CurrentSaveVersion`，旧档拒绝加载并给玩家一句明确提示（请开新局），不做逐级迁移。现有 v7–v13 逐级迁移链（当前升到 v14）仅为调试方便保留——让开发期旧档续跑、顺带验证迁移机制——**不是兼容义务**，可随时删除或简化。
- 边界：不降低「同一版本内确定性可复现」的要求（复现契约见 [08 确定性](../08-determinism-known-issues.md)）；不授权删除用户数据——拒绝加载只是拒绝，备份与文件保留；不豁免原子提交等既定开发纪律；正式发布之后恢复兼容纪律，届时另立 ADR 取代本条。

## 被否掉的替代方案

- 上线前维持逐级迁移纪律：每次破坏都要写迁移与配套测试，成本高、收益为零，还拖慢事件 ID、DSL 与 API 形状的迭代。
- 兼容开关 / 双轨兼容层：制造伪兼容，测试面翻倍，且违反「校验必须显式失败、不静默降级」的既定纪律。
- 冻结存档格式与内容 ID 直到上线：等于停止迭代，不现实。

## 后果与代价

- 接受：上线前任何一次升版都可能让既有存档无法续玩，拒绝提示必须明确；历史 parity 基线、轨迹转储与采样数据可随时因机制变化作废，作废不再需要兼容性理由。
- 推翻并就地改对的既有条款：
  - [07 存档版本与兼容规则](../07-save-compatibility.md) 的迁移纪律（§7「必须审查兼容、拒绝或迁移」与 §8 检查清单的迁移表述）改为硬切断为默认。
  - [known-issues KI-3](../../references/known-issues.md) 的基线重建口径改为：上线前基线不承担兼容义务，重建是求当前正确的手段而非义务。
  - [06 扩展指南](../06-extending.md) 「需要旧档获得新实体时，必须显式迁移并提升版本」改为非强制。
- 禁止：以本裁决为由降低同版本确定性要求、删除用户数据文件、豁免原子提交或测试纪律；禁止把无兼容义务延伸到正式发布之后。
